- Изменение workflow: [развёртывание](skills/agent-setup/references/deployment.md), [spec-authoring](skills/agent-setup/references/spec-authoring.md).
- Утилиты переноса/реестров: [контракт и поставка](skills/agent-setup/references/workspace-tools.md); регрессии CLI — `python3 -B -m unittest discover -s scripts -p test_workspace_tools.py -v`. Это тесты файловых операций в temp, не запуск agent-setup.
- Контекст/локальные нормы: [CORE](skills/agent-setup/references/practices/CORE.md).
- Практики: [меню](skills/agent-setup/references/practices/README.md), [формат карточки](skills/agent-setup/references/practices/STANDARD.md), [краткие решения](skills/agent-setup/references/choices.md).

- Шаблоны: [каталог](skills/agent-setup/assets/templates/README.md); сохранять `.template.md` и проверять конечные пути при адаптации.
- Поставка auto-improve: [исходник](skills/agent-setup/assets/templates/auto-improve.template.md), [контракт установки](skills/agent-setup/references/deployment.md#5-что-оставить-для-развития). Наличие текста сопровождения не заменяет локальный skill.
- Приёмка/выпуск: [задания](skills/agent-setup/references/acceptance.md), [release](docs/release.md).

## Правила изменения

Сначала прочитать затронутый канон и текущий Git diff, сохранить чужие правки. Менять минимально достаточную область, обновлять связанные маршруты/шаблоны/версию. Новый файл оправдан функцией и достижим из входов. Операционные и управляющие инструкции, файловые/внешние области, Git и MCP — части устройства.

Каждый skill должен оставаться переносимым при копировании одной его папки. Не добавлять зависимости на абсолютные личные пути, соседний checkout или внутренние источники. Примеры нейтральные, секреты и реальные клиентские данные не публикуются. У каждого исполняемого компонента явно названо, что он проверяет; статический pass не является успехом поведения.

Локальные зеркала `.agents/skills/agent-setup` и `.claude/skills/agent-setup` указывают на один канон; не редактировать их как независимые наборы. Проект использует отдельный Git, основная ветка main, remote — публичный GitHub. Commit должен содержать только относящиеся к задаче изменения; push/публикация — в рамках поручения.

Проверка структуры пакета: `python3 scripts/check_package.py`. Она читает пакет, не настраивает тестовый проект и не вызывает модель/внешние системы. На первом выпуске запуск настройки/поведенческие испытания оставлены пользователю по явному поручению. При будущих прогонах записывать ожидание/факт/вердикт, не менять not-run задним числом.

После значимой обратной связи: наблюдение (особенно направляющее замечание пользователя) → причина → предложение улучшения → согласование → правка канона → относящаяся проверка → обновление версии/ограничений. Общий вызов auto-improve не разрешает внедрение новых идей. Конкретно порученное/одобренное улучшение выполнять без повторного запроса; остальные предложения предъявлять пользователю до внедрения.

В отсылках к ID указывать краткое имя/суть каждой стороны связи, включая таблицы решений. Настроечные файлы целевых пространств по умолчанию в setup/; миграция сохраняет локальные каноны и пересчитывает ссылки/пути проверок. Статические фикстуры helper: `python3 -B scripts/check_auto_improve_fixtures.py`; это не пробный запуск агентского workflow.
