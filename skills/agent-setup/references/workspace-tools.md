# Скрипты перемещения и производных реестров

Читать при выборе V27 (перенос) или автоматизации V19/V08 (реестры), установке инструментов и сопровождении пространства. Это поставляемый код с настраиваемым корнем/конфигурацией, без зависимости от проектов автора. Реализации используют опыт рабочих PM-проектов: предпросмотр ссылок и реестры из метаданных; исходные проектные оси, пути и словари не переносятся.

## 1. Поставка в проект

| Функция | Что скопировать из scripts этого skill в scripts проекта | Зависимости |
| --- | --- | --- |
| Перемещение с пересчётом Markdown-ссылок | [move_artifacts.py](../scripts/move_artifacts.py) и [workspace_paths.py](../scripts/workspace_paths.py) | Python 3.10+, стандартная библиотека |
| Генерация реестров | [build_registries.py](../scripts/build_registries.py) и тот же workspace_paths.py | Python 3.10+, PyYAML; [requirements.txt](../scripts/requirements.txt) |

Это комплект: общий workspace_paths.py должен лежать рядом с установленными CLI. Для генератора установить зависимость в принятую среду проекта, например `python3 -m pip install -r scripts/requirements.txt`, сохранив выбранный проектом способ управления зависимостями. Если устанавливается только перемещение, PyYAML не нужен. В пакет включены исходники, зависимость не вендорится.

Выбирать нужные функции под согласованный процесс. Установить копии в целевой проект; не оставлять абсолютную ссылку на компьютер настройщика. Зафиксировать версию пакета и локальные изменения; обновлять комплект сравнением, не перезаписывать пользовательский diff. Включить команды в локальную инструкцию сопровождения/проверок с условием применения. Пример конфигурации реестра — [registry.template.yaml](../assets/templates/registry.template.yaml).

## 2. Перемещение

Пути OLD/NEW задаются относительно явного корня. Без --apply файлы не меняются:

```bash
python3 scripts/move_artifacts.py --root . --move notes/N-01.md guides/N-01.md
python3 scripts/move_artifacts.py --root . --move notes/N-01.md guides/N-01.md --apply
```

Можно повторять --move для независимых файлов/каталогов. Перемещаются сами источники и пересчитываются входящие и исходящие ссылки в .md/.mdc; ссылки между одновременно перенесёнными документами сохраняют смысл. Предпросмотр показывает пути и unified diff. Конфликт существующего назначения, выход за корень, пересекающиеся/цепочные перемещения, symlink и перенос каталога с вложенным Git отвергаются до записи. Обмен путями и циклы выполнять отдельной явно спланированной миграцией, они не поддерживаются этой командой.

Поддержаны однострочные inline/image-ссылки и reference definitions, URL-encoded имена, angle-адреса с пробелами, скобки в имени, title, query/fragment. Fenced/inline/indented code не переписываются; внешние URL, корневые URL и локальные #якоря остаются. Содержимое якорей не валидируется и не переименовывается. Это ограниченный Markdown-парсер, а не обещание поддержки любого CommonMark/MDX-синтаксиса.

HTML, wiki-ссылки, многострочные адреса, path-поля YAML/JSON, CLI-аргументы, конфигурации, Git remotes и вложенные repo требуют отдельной проверки. Скрипт сообщает о вероятных строковых потребителях старого пути в конфигурациях/коде и блокирует --apply до их разбора. Флаг --allow-unhandled означает, что для названных потребителей принят отдельный план исправления; сам он их не меняет. Поиск таких потребителей эвристический, а не доказательство отсутствия других зависимостей.

По умолчанию не сканируются технические каталоги (.git, .venv, node_modules и т.п.) и symlink. Дополнительные --exclude принимают сегмент пути или fnmatch. Архив не исключается из переноса автоматически: если выбрано --exclude archive, ссылки внутри него намеренно остаются вне охвата и это надо указать при приёмке.

При обычной ошибке записи скрипт пытается вернуть уже изменённые байты и перемещения; сбой восстановления сообщается явно. Это не транзакционная файловая система: аварийное завершение процесса, отключение питания и все гонки не покрыты. До миграции иметь принятое средство восстановления; Git-команды скрипт не выполняет. После переноса исправить объявленные конфигурационные потребители, пересобрать производные реестры и выполнить местные проверки ссылок/маршрутов. Сам перенос не доказывает сохранение всего процесса.

## 3. Реестр из метаданных

Адаптировать registry.template.yaml как `<область>/registry.yaml`. Новый раздел не обязан автоматически получать генератор: маленький ручной реестр остаётся допустимым решением V19. Если генератор выбран, его область и поля задаются явно:

```bash
python3 scripts/build_registries.py --root . --config notes/registry.yaml
python3 scripts/build_registries.py --root . --config notes/registry.yaml --apply
python3 scripts/build_registries.py --root . --config notes/registry.yaml --check
```

Без --config обнаруживаются registry.yaml по всему корню, кроме технических и архивных каталогов. Повторяемый --config ограничивает набор конфигураций. Предпросмотр и --check не пишут файлы; --check возвращает 0 при совпадении, 1 при drift/отсутствующем результате, 2 при ошибке источников. Обычный предпросмотр возвращает 0 при валидном плане даже с отличиями; запись требует --apply. --diff показывает diff также в check/apply.

Каждая конфигурация содержит version: 1, title, tables и необязательные intro/notes/output/section. Таблица задаёт include/exclude (glob от папки YAML), columns (label/field, link, fallback, required), where и sort; по умолчанию порядок по пути. Поля с точками читаются из вложенных метаданных. title берётся из frontmatter, затем из первого H1 вне fenced code. ID не угадывается из соглашений другого проекта; при необходимости поле id задаётся в источнике. Статус документа и результат проверки — разные поля, счётчики не выдумываются.

registry.summary и иные ручные сведения хранятся в frontmatter исходника. Для скриптов, вложений и неизменяемых источников использовать records того же YAML: path плюс нужные поля. Отсутствующий источник — ошибка; сознательно отсутствующий файл требует строкового unavailable с объяснением. Дубликаты YAML-ключей, конфликт records с frontmatter и неполные required-поля дают ошибку до записи всех результатов. Ссылки внутри текстовых полей метаданных пересчитываются от их источника к месту реестра; экранируются разделители таблицы.

Пример исходника, соответствующий шаблону:

```yaml
---
id: N-01
title: Проверка источников
status: draft
registry:
  summary: Как сверять факты перед выдачей справки.
---
```

По умолчанию результат — REGISTRY.md рядом с YAML; output может задать другой путь внутри корня. У каждого результата единственный владелец-конфигурация. Сначала проверяется весь выбранный набор, затем выполняется запись. Повторная сборка при неизменных источниках даёт те же байты. Ошибка записи запускает попытку восстановления уже затронутых выходов; аварийное завершение не покрывается.

## 4. Ручной текст и миграция

Полностью генерируемый файл помечен `Generated by build_registries.py`; поля правятся в источниках. Скрипт отказывается перезаписывать существующий ручной файл. Перед переходом вручную перенести его сведения в frontmatter/records/notes и сверить сохранность; генератор не извлекает смысл старого реестра автоматически и не поставляет мигратор всей истории.

Для блока в существующем README задать в YAML `output: README.md` и `section: true`, а в README поставить одну упорядоченную пару:

```html
<!-- registry:start -->
<!-- registry:end -->
```

Обновляется только содержимое между маркерами; байты ручного текста снаружи сохраняются. Отсутствующие/повторные/переставленные маркеры — ошибка. Ручные добавления внутри генерируемого блока следует перенести в источники: --check покажет drift, --apply восстановит производный результат. Генератор не читает старую таблицу как источник строк.

После подключения проверить добавление/изменение/удаление документа, ссылку из метаданных, обязательные поля, повторную сборку, check-only без записи, ручной текст вокруг блока и миграцию без потери сведений. После перемещения файла проверь include и records/path: пересчёт Markdown-ссылок не заменяет обновления отбора/конфигурации реестра.
