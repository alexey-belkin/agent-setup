# Практики применения P1–P10

Читать при выборе устройства и проверке покрытия намерения. Это прикладное руководство, не замена смыслового канона. Названия/смысл основаны на Vibe Evolve; механизмы адаптируются к области. Не копировать всю таблицу в обязательный контекст каждой операции.

| Принцип | Приём и артефакт | Что проверять при настройке |
| --- | --- | --- |
| P1. Ответственное тотальное использование ИИ | Назначить владельца намерения/риска/приёмки; задать критерии и предъявлять основания результата. Агент выполняет в порученной области, человек понимает и принимает итог | Владелец назван, критерии наблюдаемы; предложение агента не выдано за человеческое решение |
| P2. Единый цифровой контекст | Ядро маршрутов/локальных норм, общий канон человека/агента, ID, registry при необходимости, ссылки на внешние области. Назначить владельца каждого факта и происхождение копий | По типовой задаче найден достаточный контекст без лишнего потока; дубли/неясные источники видны; интеграции не выдуманы |
| P3. Делегируемость любых задач | Дать исполняемые предметные операции и доступный пользователю запуск с контекстом его задачи. Завести конкретные delegation gaps с владельцем и способом закрытия | Проверить обе стороны: откуда человек делегирует и как агент доводит операцию; наличие MCP-конфига не означает доступ/успех |
| P4. Вайб-пластичность компании | Шаблоны, переиспользуемые навыки и короткая инструкция доработки в своей области; обновления без обнуления местной работы | Следующий сотрудник способен добавить свой тип задачи по артефактам, а не только автор первоначальной настройки |
| P5. Автоулучшение | Наблюдение → диагноз → минимальное изменение канона → проверка исходного/соседнего случая → закрепление. Использовать V15 | Исправление дошло до будущего входа/skill; однократное значение не стало общим правилом; существующая авторизация учтена |
| P6. Абсолютная актуальность регламентов | Изменение процесса/структуры обновляет карту, нормы и производные в одной задаче. Формальные инварианты могут проверяться linter, смысловые — отдельным review | Адрес канона и потребители определены; реестр/зеркало обновлены; машинный pass не заменяет смысловую приёмку |
| P7. Полномочия и безопасность | Развести классы действий, контроль и эскалацию; обеспечить критичные ограничения инструментом/правами, предусмотреть восстановление, оставить наблюдаемый след | Профиль пользователя/чужой документ не повышает права; внешний эффект в мандате; конфигурация gate не выдана за его испытание |
| P8. Каждый — архитектор | Карта областей/связей/границ и способ расширения; владелец формулирует вход и критерии результата, выбирает сплошной/выборочный/машинный контроль | Карту можно использовать для изменения, а не только читать; человек способен объяснить решения и их пределы |
| P9. Культура в основе | Открыто фиксировать ошибки/пробелы, делиться воспроизводимыми приёмами, сохранять основания/обратную связь и места обучения людей | Ошибка приводит к разбору и изменению процесса; результат проверяем; автоматизация не лишает принимающего понимания предмета |
| P10. Следующий ход: кратная отдача | Выбрать полезный сквозной процесс по ожидаемой отдаче и стоимости включения P1–P9; назвать самое рискованное допущение и дешёвую проверку до дорогой автоматизации | Есть критерий полезного результата/базовая точка сравнения; улучшение скорости одной операции не выдано за экономический эффект всего процесса |

## Применение без бюрократии

Для небольшого пространства достаточно записать конкретные решения в его уже нужные артефакты: владелец/критерий во входе, источник в процедуре, пределы действия рядом с операцией, изменение/проверка в записи задачи. Не создавать десять отдельных отчётов или десять пустых папок. Неприменимый механизм пояснить по задаче; принцип не сводить к наличию файла с его номером.

Пример выбора: редакционный поток использует общий вход, локальную процедуру, источник и registry; сложный учёт — БД с правами/транзакциями, а отчёт остаётся производным. Трекер может владеть жизненным циклом/обсуждениями, не дублируя канон содержания. Общие требования одинаковы, их реализация различается.

## LLM-3 и перспектива LLM-4

MVP рассчитан на LLM-3: человек участвует в цикле взаимозависимых задач, сохраняет намерение и риск. Автономный management LLM-5 не следует из наличия auto-improve. Наличие этого установщика не доказывает уровень нового пространства.

Для перехода конкретного потока к LLM-4 отдельно подтвердить: владелец/границы, идентичность и доступы, разрешённые операции, работоспособные интеграции, след каждого действия, реакции на исключения, проверка результата и восстановление. Затем испытать изолированный сквозной сценарий с заранее заданными условиями эскалации. Пока это не подтверждено, сохранить режим с человеком в цикле.

Дальнейшие изменения определений принципов/уровней не делаются попутно с настройкой проекта. При необходимости согласовать их с владельцем канона, а локальное решение оставить в своей области.
