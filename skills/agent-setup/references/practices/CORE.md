# Ядро проектирования агентского пространства

**Редакция:** 02.11.2026. **Статус:** базовые требования пакета по решению автора. Читать при проектировании или изменении пространства; в обычной задаче действовать по уже принятым локальным инструкциям.

V03 (маршруты достаточного контекста), V23 (достижимость) и V20 (локальность инструкций) входят в ядро, а не выбираются из меню как независимые опции. Старые ID сохранены для трассировки. Ядро задаёт свойства пространства; конкретные файлы, механизмы проверки и структура выбираются по задачам. Это прикладное ядро настройки, не изменение определений методологии Vibe Evolve.

## 1. Четыре правила

1. **Минимум действий до достаточного контекста.** Оптимизировать число чтений для конкретной задачи, а не длину AGENTS саму по себе. Короткое общее правило, нужное почти в каждой задаче, оставить во входе. Не выносить его в файл, который всё равно придётся открывать каждый раз. Уже загруженный и не изменившийся контекст повторно не читать; независимые нужные фрагменты можно получить одним действием в пределах бюджета.
2. **Ограниченная порция.** Рабочий предел MVP — до **15 000 токенов одной загружаемой порции**. Это предложенный автором ориентир для проектирования, не новый предел окна Claude/Codex. Считать фактически подаваемую порцию: один файл, выбранный раздел или суммарный вывод пакетного чтения. Если нужен больший источник — выбирать разделы по задаче или делить на самостоятельные модули с понятным маршрутом. Не обрезать источник молча. Короткость оценивается вместе с достаточностью; 15 000 — потолок, а не целевой размер AGENTS.
3. **Достижимость и понятный выбор ссылки.** Из AGENTS и навыков можно дойти по логичным ссылкам до почти любой нужной части контекста. Рядом со ссылкой понятно, при какой задаче её читать и что там найти. Проверка существования ссылки и проверка маршрута — разные проверки. Для исключённых архивов, сырых выгрузок и больших данных явно задать способ поиска/доступа; не оставлять их случайно оторванными. Ссылка на якорь сама по себе не гарантирует, что инструмент загрузит только раздел: выбирать нужный диапазон/операцию чтения.
4. **Общий контекст людей и агентов.** Факты, решения, инструкции и результаты общие. Различаться может UI: редактор, граф, таблица, сайт, чат. Разделять документы по функции, области, жизненному циклу или размеру, а не по признаку «этот для человека, тот для агента». Производное представление имеет источник и способ обновления, а не независимый канон.

## 2. Локальность инструкций (V20)

Общий вход содержит короткие нормы, нужные всему проекту, и прямой выбор маршрута. Правила области действуют в своём стриме/папке/процедуре и доступны при попадании задачи в эту область. Общие нормы не копируются во все локальные файлы; исключение или переопределение имеют явные границы и основание.

Локальные правила могут жить в AGENTS.md, README.md, skill или разделе существующего документа. Отдельный файл нужен при самостоятельной функции/объёме; создавать его в каждой папке автоматически не требуется. Проверяется, как выбранный harness фактически получает эти правила: само наличие README или файла с нужным именем не доказывает чтения.

[V18](V18-root-instruction.md) описывает реализацию общего входа, [V19](V19-folder-registry.md) — навигацию папки. Их варианты подчинены этим базовым свойствам. Машинная достижимость сама по себе не доказывает, что агент понимает, какую ссылку выбрать.

## 3. Как спроектировать маршрут

1. Выбрать тип задачи и обязательные факты/правила для неё.
2. Назвать каждый переход: условие → адрес/раздел → что получаем. Если решение уже можно принять из AGENTS, идти прямо в нужный стрим/skill/объект.
3. Для нового отдельного файла записать функцию и условие чтения. Удалить промежуточный индекс, если он не помогает выбирать; объединить постоянно читаемые короткие сведения, если они укладываются в бюджет.
4. Измерить порции и сумму их объёмов; отдельно посчитать необходимые чтения. Бюджет одной порции не разрешает загружать десятки лишних маленьких файлов.
5. Проверить несколько разных задач: маршрут B не обязан проходить через спецификацию A или общую спеку устройства. Межстримовая задача читает только затронутые связи.
6. Проверить ссылки и отсутствие непреднамеренно недостижимых собственных Markdown-артефактов. Проверить сценарий выбора маршрута; затем подтвердить достаточность реальной тестовой задачей, а не только графом ссылок.

## 4. Проверка ядра

До передачи пространства подготовить несколько характерных задач: операция одного стрима, межстримовая задача и изменение структуры. Для каждой назвать достаточные нормы/данные, маршрут чтения, число действий и объём порций. Проверить достижимость и исключения, затем дать задачу в новой сессии без истории настройки и сопоставить результат с ожидаемым.

Ядро обязательно как контракт проектирования; это не утверждение, что конкретное пространство уже прошло такую проверку. Выбор symlink/копий, registry, frontmatter, БД или трекера зависит от задач и не следует автоматически из обязательности контекста.
