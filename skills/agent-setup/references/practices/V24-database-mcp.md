# V24. БД как связанное хранилище с доступом по MCP

**ID:** V24. **Версия:** 0.1. **Редакция:** 02.11.2026.
**Форма реализации:** модель данных, сервис операций, MCP. **Описание:** на ревью. **Поведенческая проверка:** not-run.

## 1. Когда выбирать

Сущности имеют много связей, расчёты/выборки пересекают их, несколько участников меняют данные, файловые таблицы дают противоречия. Результат — единый канон данных и контролируемые операции агента. Нужны владелец схемы/данных, обслуживание БД, права и восстановление. Небольшой независимый реестр без сложных выборок дешевле оставить файлом.

Решение принимается для области данных, не для проекта целиком: инструкции и документы могут оставаться в файлах, жизненный цикл — в трекере.

## 2. Как работает

1. Определить сущности, устойчивые ключи, связи и ограничения. Описать смысл полей, единицы измерения, первичные и производные данные. БД владеет выбранными фактами; XLSX/отчёт — импорт или производная копия с указанной версией/датой.
2. Предоставить агенту схему и ограниченный слой операций через MCP: чтение/поиск, изменение в пределах роли, расчёт/экспорт. Проверка аргументов и прав выполняется инструментом/БД, а не только текстом skill.
3. Изменение проходит в транзакции, с валидацией связей и защитой от потерянного обновления (например, версия записи). Для повторного запроса использовать ключ операции, если повтор может создать дубль.
4. Для изменения схемы/массовой операции определить миграцию, резервную копию и проверенное восстановление. Снимок не заменяет транзакцию и не отменяет решение о допустимости потери последующих данных при откате.
5. Импорт проходит staging/валидацию до канона; экспорт не редактирует канон обратно без отдельного протокола. Производные расчёты имеют источник и способ пересчёта.

## 3. Варианты и сочетания

| Вариант | Когда выбирать | Цена / ограничения |
| --- | --- | --- |
| Предметные MCP-операции | Повторяемые изменения и ограниченные роли | Нужно разрабатывать/сопровождать API; проще выразить допустимое действие |
| SQL для анализа под read-only ролью БД | Нестандартные выборки, известная схема | Ограничивать объём/время; название метода SELECT не обеспечивает read-only |
| SQL/DDL с широкими правами | Разрешённое сопровождение схемы | Другая роль/контур, журнал и восстановление; нельзя отдавать как обычный инструмент всем |

Обязательны реальная БД, исполняемый MCP-сервис и права; карточка их не поставляет. [V25](V25-tracker-lifecycle.md) может хранить согласование операции, но не становится вторым каноном строк БД. Для сложного хранения схема и документация важнее самого выбора MCP-транспорта.

## 4. Минимальный пример

Алгоритмический пример учёта вымышленного оборудования, без финансовых/персональных данных:

```text
Room(id, name)
Device(id, room_id -> Room.id, label, revision)
move_device(device_id, target_room_id, expected_revision, operation_key)
```

Устройство D-01 находится в R-01 с revision=3. Разрешённая операция переноса в R-02 проверяет существование комнаты и expected_revision=3, меняет комнату и увеличивает revision до 4 в одной транзакции. Повтор с тем же operation_key возвращает результат прежней операции. Конкурентный запрос с revision=3 после изменения получает конфликт и не затирает новые данные. Экспорт показывает D-01/R-02, время и источник выборки. Это контракт, не готовый сервер.

## 5. Внедрение и развитие

Выбрать канон, схему, роли чтения/изменения, границы импортов/экспортов, журнал и резервирование. В карте пространства обозначить БД, MCP, файлы схемы/миграций, пользователей и потребителей. Секреты подключения хранить вне распространяемых инструкций/профиля пользователя. Skill описывает предметную процедуру и когда читать схему; не содержит постоянную копию изменчивых данных.

Начинать с чтения на тестовых данных; запись допускать после проверки ограничений и восстановления. При изменении схемы обновить миграцию, API, импорты/отчёты и связанные нормы. Откат кода не откатывает БД автоматически; нужен план совместимости/восстановления данных. Полный аудит безопасности конкретного сервера — отдельная работа.

## 6. Приёмка и границы

**Статус исполнения кейсов:** not-run; только в изолированной БД с вымышленными данными.

| Кейс | Исходное состояние и действие | Ожидаемый наблюдаемый итог |
| --- | --- | --- |
| V24-T1 | Выполнить перенос D-01 и повторить operation_key | Одна смена комнаты, revision=4; повтор не даёт второго изменения |
| V24-T2 | Несуществующая комната или устаревшая revision | Ошибка/конфликт без частичной записи; исходная согласованность сохранена |
| V24-T3 | Аналитическая роль пытается UPDATE через SQL-инструмент | БД/сервис запрещает запись; одного обещания в инструкции недостаточно |
| V24-T4 | Разрешённая тестовая миграция и восстановление | Проверено согласованное состояние и ожидаемые строки после восстановления; след сохранён |

MCP не гарантирует ни корректность SQL, ни разграничение доступа. **P2:** явный канон и происхождение копий; **P3:** предметная операция делегируема; **P7:** права/транзакции/восстановление ограничивают последствия. Наличие сервера не доказывает готовность автономного процесса.
