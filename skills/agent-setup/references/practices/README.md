# Библиотека практик

**Версия формата:** 0.1, 02.11.2026. Девять карточек подготовлены; V32 добавлена после одобрения расширения. Выполнена собственная сверка по источникам и кабинетным сценариям; применение карточек отдельным агентом пока **not-run**. Это меню подходов, не обязательный комплект для каждой настройки.

Читать при проектировании нового процесса или изменении существующего. Для обычной предметной задачи читать уже принятые локальные инструкции своего пространства, а не всю библиотеку. Отбирать по задаче, затем читать только подходящие карточки.

## Базовое ядро

[CORE.md](CORE.md) задаёт обязательные свойства проектирования: достаточный контекст минимальным маршрутом (V03), достижимость (V23), локальность инструкций (V20), обязательный установленный auto-improve (V15). Их не выбирают как независимые опции; способ реализации адаптируется к задаче. Локальный файл в каждой папке не обязателен. Читать ядро при проектировании/изменении пространства, а не заново перед каждой предметной операцией.

Подробный механизм обязательного компонента ядра — [V15. Auto-improve](V15-auto-improve.md); его поставка не зависит от выбора опций ниже.

У карточек стабильные V-ID из исходного реестра. Меню не исчерпывает библиотеку будущего пакета: V01–V32 и дополнительные находки ещё требуют разбора; например, генерирование реестров V08 и смысловое rubric-ревью V17 не объявлены реализованными отдельными карточками.

В выпуске v0.1 краткие инструкции ещё не оформленных подробными карточками механизмов находятся в [choices](../choices.md); это рабочие ориентиры выбора; [скрипты переноса и реестров](../workspace-tools.md) поставляются отдельно, остальные механизмы не объявляются готовыми сервисами.

## Как собрать процесс

Для каждой области/стрима зафиксировать `V-ID (название практики)@версия, AREA-ID (название области), решение, вариант, параметры, основание, проверка`. Проверить совместимость и назначить канон каждому факту. Не переносить карточку целиком в AGENTS; оставить в проекте адаптированную норму и необходимые рабочие артефакты.

**Вымышленный пример смешанного проекта:** редакционный поток получает V18 с прямым маршрутом к редакционным правилам и V19 как раздел README; учёт оборудования — V24, только если реально нужны связи и совместные изменения. V26 содержит предпочтения языка и личный путь экспорта, но не разрешение публиковать. V25 выбирается для командной приёмки обоих потоков лишь при существующей потребности в трекере. V07 нужен при втором harness. V16 контролирует ссылки и метаданные, а V15 разбирает конкретные сбои и меняет выбранный канон. Это иллюстрация выбора, не готовая установка.

При отсутствии БД/трекера проект может оставаться файловым. Разные варианты допустимы в разных стримах, если общие точки входа, источники правды и обмены согласованы.

## Для автора библиотеки

- [Стандарт](STANDARD.md) — границы карточки/реализации/сборки, переносимость, извлечение и проверка; читать при изменении формата или карточек.
- [Шаблон карточки](practice.template.md) — исходник новой карточки; заполнить содержанием и удалить подсказки.

Внутренняя трассировка источников и результаты проверки ведутся отдельно от переносимого каталога. Карточки самостоятельны: личные проекты автора для применения не нужны. Их наличие не подтверждает установку интеграций, успешный прогон или достижение LLM-4.

### Зафиксированные границы новых практик

- **V28. Передача между сессиями:** состояние задачи, решения, артефакты, открытые вопросы и следующий шаг; продолжение без истории чата. Не дублировать весь журнал операций.
- **V29. Приёмка по тестовым задачам:** отдельная сессия, исходные данные, ожидание, фактические артефакты/помощь и вердикт. Подготовка теста отделена от его исполнения.
- **V30. Git — командная работа с файлами проекта:** распределение изменений между людьми/агентами, история и версии, ветки/review/интеграция, конфликты, сохранность чужих правок, общая площадка/remote, ignores и правила commit/push. Worktree — частный способ изолировать параллельные рабочие копии; участниками команды могут быть агенты. Изоляция не заменяет согласование общей схемы и слияние результата. Установка GitHub или обязательный remote не следуют из выбора Git.
- **V31. Происхождение и статус утверждений:** первичный материал, извлечённый факт, заявление поставщика, предложение агента и принятое решение; версии/даты и потребители. Отличается от V09: V31 объясняет, откуда и с каким статусом взято утверждение; V09 — где его канон редактируется и как обновляются копии.
- **V32. Frontmatter:** [карточка создана](V32-markdown-frontmatter.md); подключается к V21/V04/V05/V09 и к реестрам/проверкам при наличии потребителей метаданных. Поля и семантика определяются типом артефакта, не копируются одинаково во все `.md`.

V09 одобрена как самостоятельная практика: назначение канона по виду факта, роли рабочих/производных копий, обновление и разрешение расхождений. В V27 проверить и входящие, и исходящие ссылки: текущий исходный скрипт исправляет лишь часть задачи. Первоисточники всех новых карточек ещё требуют критического разбора; очередь не ограничивает поиск другими найденными механизмами.
