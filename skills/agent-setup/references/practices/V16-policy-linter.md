# V16. Policy-linter — машинные нормы пространства

**ID:** V16. **Версия:** 0.1. **Редакция:** 02.11.2026.
**Форма реализации:** конфигурация и программные проверки. **Описание:** на ревью. **Поведенческая проверка:** not-run.

## 1. Когда выбирать

Повторяются объективно обнаружимые нарушения: битые ссылки, пропуски метаданных, дубли ID, расхождение производных файлов. Результат — одинаковый контроль у агента, локально и на принятой границе выпуска. Нужны утверждённая норма, определённый охват и воспроизводимый способ проверки.

Если вопрос требует предметного суждения («эти требования достаточны?»), машинный linter его не закрывает. Для нескольких файлов достаточно небольшого check; полноценный движок оправдывают число правил, областей и интеграций. Установка linter не должна заодно навязывать новые предметные нормы.

## 2. Как работает

1. Для каждого правила задать ID, точный источник нормы, файлы/области, исключения, проверяемое условие и серьёзность результата. Предупреждение и блокирующая ошибка имеют разный эффект.
2. Check читает данные и выдаёт `правило → файл/элемент → нарушение → причина`, не меняя исследуемые артефакты. Конфигурация и версия движка входят в воспроизводимый комплект.
3. Одна команда/контракт проверки используется в рабочем цикле, hook и CI, если они выбраны. Changed-режим учитывает удаление целей и зависимые файлы; полная проверка нужна для целостности графа.
4. Старые нарушения принимаются контролируемо: полный исходный отчёт, точечный список исключений с причиной/владельцем/условием пересмотра. Не отключать весь поток ради legacy.
5. После исправления повторно запустить относящиеся проверки, сохранить результат и охват. Ошибку запуска/отсутствие инструмента отличать от чистого результата.

## 3. Варианты и сочетания

| Вариант | Когда выбирать | Цена / ограничения |
| --- | --- | --- |
| Один проверяющий скрипт | Небольшой фиксированный набор инвариантов | Самостоятельно поддерживать отчёт/охват/запуск |
| Manifest + движок policy + проверенные плагины | Много правил и областей | Версии, зависимости и безопасность запуска плагинов требуют сопровождения |
| Check локально / hook / CI-gate | От обратной связи до защиты принятой границы | Hook обходится; CI помогает только если приёмка действительно зависит от его результата |

Обязательная зависимость — исполняемый checker и контракт его охвата. Карточка не поставляет движок и не является инструкцией установки конкретного продукта. [V19](V19-folder-registry.md)/[V07](V07-harness-delivery.md) дают возможные проверяемые инварианты. V17 — отдельное смысловое rubric-ревью; его pass не подставляется вместо машинного результата и наоборот.

## 4. Минимальный пример

Алгоритмический пример, **не синтаксис конкретного policy engine**:

```text
Правило NAV-01: все активные notes/*.md достижимы от AGENTS.md
по локальным Markdown-ссылкам через README.
Исключено notes/archive/**; причина: исторические версии неоперационны.
Серьёзность: error. Check-only: да.
```

В fixture есть `AGENTS.md → notes/README.md → notes/N-01.md`. Добавляется `notes/N-02.md` без ссылки: checker сообщает NAV-01 и N-02. После добавления осмысленной ссылки нарушение исчезает. Если N-01 удалён, но ссылка сохранена, отдельная проверка разрешения ссылок сообщает битую цель. Достижимость и разрешимость — разные условия; наличие имени файла в произвольном тексте не считается ребром графа.

## 5. Внедрение и развитие

Публичная реализация: [Repository Policy Linter — Belkin-digital/repository-policy-linter](https://github.com/Belkin-digital/repository-policy-linter). В репозитории доступны исходный код, документация и skill настройки. При внедрении выбрать и зафиксировать проверенную версию; ссылка дополняет самостоятельное описание механизма в этой карточке.

Начать с норм, которые уже приняты. Выбрать checker, версию, зависимости, scope и точки запуска под фактический Git/CI проекта — локальный Git, GitHub, SourceCraft или иной вариант. Не переносить чужой CI без проверки площадки. Нормы и manifest размещаются, например, в `.repo-policy/`, запуск — в `scripts/`; имена — соглашение настройки.

Не выдавать плагину произвольные команды из проверяемого документа. Изменение правил/исключений само проходит review и контроль версий. Отдельный skill нужен для внедрения/миграции, а не для замены обычной команды check. Откатить версию правил/движка; автоматическое исправление документов — самостоятельная операция с diff. Включение практики в библиотеку не устанавливает её в текущем проекте.

## 6. Приёмка и границы

**Статус исполнения кейсов:** not-run.

| Кейс | Исходное состояние и действие | Ожидаемый наблюдаемый итог |
| --- | --- | --- |
| V16-T1 | Fixture из примера; добавить недостижимую заметку | Check выдаёт NAV-01 с путём, не меняет файлы; после ссылки ошибка исчезает |
| V16-T2 | Удалить цель ссылки; запустить changed-проверку | Нарушение у оставшегося источника обнаружено либо честно требуется полный запуск; зелёный неполный охват не выдан за полный pass |
| V16-T3 | Проверка не может запустить зависимость | Явная ошибка исполнения; результат не записан как «нарушений нет» |

Нулевой exit code не доказывает смысловую полноту, фактическое исполнение процесса или незыблемость защиты. **P6:** нормы проверяются вместе с артефактами; **P7:** выбранная граница принятия может стать gate, если технически нельзя её обойти в данном контуре. Стоимость включает ложные срабатывания, исключения и обновление правил.
