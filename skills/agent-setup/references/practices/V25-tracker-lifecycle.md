# V25. Жизненный цикл и командная коммуникация в Tracker

**ID:** V25. **Версия:** 0.1. **Редакция:** 02.11.2026.
**Форма реализации:** протокол обмена, skill и MCP. **Описание:** на ревью. **Поведенческая проверка:** not-run.

## 1. Когда выбирать

Команда уже использует трекер или ей нужны общие статусы, назначения, обсуждения и след решений по артефакту. Результат — контент и ход работы связаны без ручного пересказа между системами. Нужны доступ к выбранному проекту/очереди, MCP-операции и договорённость, чем владеет трекер. Не создавать второй workflow для одиночной файловой задачи без такой потребности.

## 2. Как работает

Назначить канон **по виду факта**, не по системе целиком. В распространённом варианте нормализованное содержание/AC живут в файле; детальные статусы, исполнители, комментарии/решения, worklog и иерархия — в Tracker. Первичное требование может появиться в комментарии трекера и сохраняет своё происхождение после нормализации. Возможен иной выбор, если он явно принят.

1. Артефакт хранит ключ/ссылку на карточку; карточка — путь/URL на доступную команде редакцию артефакта. Локальный путь владельца не считается общей ссылкой.
2. Перед изменением агент читает текущую карточку, относящиеся комментарии/решения и доступные переходы. Он не угадывает ID перехода по знакомой другой очереди.
3. В пределах поручения меняет содержимое/состояние. В комментарии фиксирует результат, точную редакцию/ссылку, что проверено и что требуется от команды. Коммуникация через комментарии — внешнее действие и требует соответствующего поручения.
4. При обратном потоке фиксирует автора, дату, исходную формулировку и основание принятия; технический автор комментария не равен лицу, одобрившему решение. Конфликт с каноном не перезаписывается молча.
5. Между Git/файлами и Tracker нет общей транзакции. При частичном успехе сохранить ключ и фактическое состояние, затем восстановить отсутствующую связь/шаг; не создавать дубли повторным запуском.

## 3. Варианты и сочетания

| Вариант | Когда выбирать | Цена / ограничения |
| --- | --- | --- |
| Файлы — содержание; Tracker — процесс и обсуждения | Артефакты рецензируются/версионируются отдельно | Нужны ссылки на принятую редакцию и протокол синхронизации |
| Tracker — также канон содержания | Команда принимает его поля/описание как основную запись | Файлы становятся производными; нельзя редактировать две независимые версии |

Обязательная зависимость — доступные операции чтения и разрешённых изменений. Для Yandex Tracker использовать реальные схемы MCP и переходы конкретной очереди; транспорт может быть прямым или через сервисный шлюз. [V26](V26-user-local.md) задаёт личные параметры, но не права; [V24](V24-database-mcp.md) может владеть предметными данными, отличными от статуса карточки.

## 4. Минимальный пример

Иллюстрация для вымышленного DOC-01 и карточки TASK-17:

```text
DOC-01: «Порядок выдачи оборудования», версия r3, tracker=TASK-17.
TASK-17: состояние «Ревью», ответственный назначен, ссылка на DOC-01@r3.
Комментарий по поручению: «Подготовлена r3: уточнён возврат.
Ссылки проверены; предметная приёмка ожидается от владельца».
```

После замечания команды агент отделяет принятое изменение от предложения, правит DOC-01, связывает новую редакцию и сохраняет происхождение решения. Одна отправка комментария не закрывает предметную приёмку. TASK-17 и имена состояний — условные значения, не команда/ID реальной очереди.

## 5. Внедрение и развитие

Задать роли полей, область карточек, связи объектов/версий, допустимые переходы, формат результата и способ восстановления частичного обмена. Если Git используется, выбрать доступную команде ссылку конкретной версии с учётом площадки и прав; без Git хранить явный идентификатор редакции и доступное хранилище.

В skill оставить протокол и маршруты к актуальным нормам очереди, а не список временных карточек/пользователей. При смене очереди проверить поля/переходы и миграцию ссылок. Исправления истории выполнять как прозрачное уточнение/компенсацию, не стирать обсуждения. Готовый универсальный MCP-адаптер эта карточка не поставляет.

## 6. Приёмка и границы

**Статус исполнения кейсов:** not-run; выполнять на тестовой очереди/изолированной модели, не писать в рабочую команду без поручения.

| Кейс | Исходное состояние и действие | Ожидаемый наблюдаемый итог |
| --- | --- | --- |
| V25-T1 | По поручению связать DOC-01 и тестовую карточку | Обе стороны разрешаются; содержание/состояние имеют назначенных владельцев; результат содержит версию |
| V25-T2 | Файл записан, обновление карточки оборвалось | Отчёт различает оба результата; повтор восстанавливает связь без дубля карточки/комментария |
| V25-T3 | Комментарий агента предлагает изменение без человеческого решения | Не выдаётся за согласование; спорный канон/приёмка не меняются автоматически |
| V25-T4 | В другой очереди переход имеет иной ID | Агент получает доступные переходы; не применяет прежний ID наугад |

Tracker — не только dashboard: он может владеть обсуждениями, решениями, назначениями, иерархией и учётом работ. Связь сама по себе не обеспечивает актуальность. **P2:** связный контекст и происхождение; **P6:** обновление связей вместе с результатом; **P1/P7:** различимы предложение, решение и поручение на внешнее действие.
