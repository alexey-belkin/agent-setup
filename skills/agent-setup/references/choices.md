# Дополнительные решения при проектировании

Это краткие инструкции выбора одобренных механизмов, для которых в v0.1 ещё нет отдельных подробных карточек. Они задают вопросы/инварианты проектирования; поставленные инструменты для V27/V08 описаны отдельно вместе с охватом и проверками, остальные механизмы не объявляются готовыми реализациями. Читать только соответствующий раздел; базовые V03/V20/V23 находятся в [CORE](practices/CORE.md), девять подробных карточек — в [меню](practices/README.md).

## V21. Шаблоны артефактов

Выбирать для повторяющегося типа результата с устойчивыми полями/структурой. Шаблон задаёт смысл секций, обязательное и условное; отдельное руководство нужно лишь при самостоятельной функции. Создавать по данным, не заполнять пробелы выдумками. Например, карточка заметки требует источник/вывод/статус проверки; незаданный источник — явный gap. При изменении шаблона определить, мигрируют ли старые документы. Проверка: следующая задача получает полезный артефакт без необъяснённых placeholders. Использует V32 при наличии потребителей метаданных, не требует YAML всем файлам.

## V22. ID файлов и сущностей

Выбирать, если нужно стабильно адресовать документы, функции, решения, вопросы или области. Назначить namespace и источник выдачи ID; новое имя/перемещение не меняет ID, удалённый ID не переиспользуется. Внутри документа элементы могут иметь локальные IDs с родительским контекстом. Например, NOTE-017 и NOTE-017/Q-02. Проверка: однозначное разрешение ссылки и отсутствие коллизии после переименования. Нумерация порядка сортировки и идентичность — разные вещи.

## V04. Разные стримы и общее ядро

Выбирать, когда виды работы имеют разные объекты/стадии/процедуры, но используют общие ресурсы. Выделить потоки и потребителей; не принимать каждую папку за самостоятельный стрим. В матрице «процесс × продукт» не путать оси. Например, один продукт проходит requirements/design/testing, а общая библиотека примеров обслуживает несколько сделок. Нормы локальны, общий источник редактируется в одном месте. Проверка: задача потока B не читает spec A без зависимости; изменение общего ресурса показывает обоих потребителей. V32 может хранить множественную принадлежность без копирования файла.

## V05. Стадии одного объекта

Выбирать, если результат последовательно проходит фиксированные этапы. Раскрыть имена стадий, вход/выход, условие перехода, возврат/отказ/передачу и источник текущего состояния. Например, новая заявка → разбор → исполнение → приёмка → завершена; документы привязаны к объекту/стадии. Папки стадий могут быть физическими или логическими; не создавать пустые артефакты для всех этапов. Проверка: конкретный объект прослеживается по цепи, включая возврат; имя папки не становится вторым статусом вопреки Tracker. Метаданные стадии задавать вместе с владельцем.

## V09. Канон и рабочие копии

Выбирать, когда один факт представлен в нескольких системах/файлах. Назначить канон по виду факта, кто может менять и как обновляются производные/копии. Возможны файл-канон, внешняя система-канон или только связь без полной синхронизации. Например, содержание требования — в Markdown, статус/обсуждения — в Tracker; БД — данные, Excel — экспорт. Копия хранит источник/версию, конфликт не решается молча по времени файла. Проверка: два разных значения приводят к канону либо явному решению владельца; частичный обмен восстанавливается без дубля. Отличается от V31, которая объясняет происхождение и статус утверждения.

## V11. Зависимости

Выбирать, если изменение одного источника влияет на несколько результатов/процедур. Ребро называет производителя, потребителя, передаваемый факт/артефакт и реакцию на изменение; достаточно таблицы в существующей карте. Например, схема БД → импорт и отчёт, общий словарь → требования и инструкции. Проверка: изменение поля выявляет оба потребителя; карта не дублирует полный алгоритм каждой процедуры.

## V27. Перенос и ссылки

Выбирать при изменении пути адресуемого артефакта. До переноса получить входящие и исходящие ссылки, ID, относительные пути, исключения и предпросмотр diff. Переносить файл и пересчитать обе стороны; проверить якоря, реестры и связанные представления. Например, заметка переезжает из notes в guides: меняются ссылки на неё и её ссылки на соседей. Поставляется [move_artifacts.py](workspace-tools.md#2-перемещение): предпросмотр, сам перенос, входящие и исходящие Markdown-ссылки. Ограничения синтаксиса, исключения и конфигурационные потребители проверяются отдельно; «заменить входящие строки» не является полной миграцией. Проверка: маршруты из входов и ссылки перемещённого файла разрешаются; спорные форматы перечислены как непокрытые.

## V06. Проектируемое, действующее, выпущенное

Выбирать, когда целевое описание ещё не равно реализации или отправленной версии. Назначить роли design/current/release и критерий переноса; не держать три независимых редактируемых канона. Например, проект требования → проверенная реализация → пакет r2 к отправке. После изменения относительно отправленного baseline может понадобиться документ с Track Changes; способ сравнения/экспорта определяется форматом, не копируется абстрактно. Проверка: изменение design не выдаётся за выпущенное; доступен неизменяемый отправленный пакет и основание следующего выпуска.

## V08. Производные реестры

Поставляемая реализация — [build_registries.py и registry.yaml](workspace-tools.md#3-реестр-из-метаданных): отдельный файл либо блок README, предпросмотр/check/apply и защита ручных сведений.

Выбирать, когда ручная навигация часто расходится с источниками. Определить schema/поля, источник каждого значения, стабильный порядок, check-only режим и сохранение ручных дополнений. Например, registry из id/description/stream/stage frontmatter. Изменение исправляют в источнике, повторная генерация стабильна; отсутствующий обязательный metadata даёт диагностику. Не нужен, если короткая ручная таблица уже достаточна. Исполняемого общего генератора в v0.1 нет.

## V12. Delegation gaps

Выбирать для конкретного неделегируемого шага. Запись: задача/шаг, барьер, влияние, доступная часть, способ закрытия, владелец и повторная проверка. Например, данные доступны, но MCP не разрешает запись — подготовить локальный результат и определить нужную операцию/право. Проверка: gap не маскируется успешной отправкой и не блокирует независимую работу; после исправления выполняется нужный сценарий, а не только меняется статус записи.

## V17. Контракты и rubric-ревью

Выбирать, если формального linter недостаточно для предметной оценки. Контракт определяет область/триггер, критерии, исполнителя, стоимость и реакцию. Например, checklist полноты требования дополняет машинную проверку metadata. Отдельно хранить машинный результат, смысловое заключение и человеческую приёмку; новая rubric не включается незаметно в каждую задачу. Проверка: намеренно плохой по смыслу, но синтаксически корректный документ не получает предметный pass лишь по linter. Реальная установка движка/контрактов — отдельная операция по его документации.

## V28. Продолжение между сессиями

Выбирать для длительной/прерываемой задачи. Сохранить намерение, принятое, фактический результат/проверку, версии/пути, открытые вопросы и точный следующий шаг в принятом месте учёта. Например, «правило обновлено, синхронизация ещё не запускалась; следующий шаг — check зеркал». Чат — вспомогательный источник, запись не дублирует все сообщения. Проверка: новая сессия продолжает с нужного шага и не считает неподтверждённую отправку завершённой.

## V29. Приёмка тестовыми задачами

Выбирать для проверки фактического поведения, передачи и изменения процесса. До прогона записать вход, задачу, ожидание и допустимые эффекты; новая сессия получает только постановку/пакет/данные, не авторское решение. Сохранить результат, помощь, вердикт и свидетельства. См. [acceptance](acceptance.md). Если запуск поручен пользователю, оставить not-run. Проверка самого формата теста не равна его успешному исполнению.

## V30. Git — командная работа с файлами

Выбирать для совместных изменений людей/агентов, версий, review и интеграции результатов. Установить repo-границы, командное основание веток/коммитов, площадку и push-направление, правила conflicts/ignores. Worktree — частная изоляция параллельных рабочих копий, где команда может состоять из агентов; он не изолирует внешнюю БД и не отменяет согласование общего формата. Проверка: два независимых изменения интегрируются без утраты чужой работы, конфликт явен. Не делать reset/force push/массовую чистку ради «чистоты» настройки. Локальный Git допустим без удалённого сервера; GitHub/SourceCraft — варианты площадки, не обязательность.

## V31. Происхождение утверждений

Выбирать для внешних материалов/решений/публикаций. Сохранять источник, автора/дату/версию и точное место; отличать извлечённый факт, заявление автора, расчётный пример, предложение агента и принятое решение. Например, заявленная поставщиком метрика остаётся заявлением до проверки. Незнание отмечается явно. Проверка: каждое существенное утверждение прослеживается к основанию и статусу; повторение в двух копиях не становится двумя независимыми доказательствами. Полезно совместно с V09/V25/V32, но не подменяет назначение канона.
